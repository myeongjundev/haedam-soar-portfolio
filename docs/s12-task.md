## 맡은 변경

`infra/s12-*.json`, 개인 S12 Graylog/n8n 생성물, `tools/*s12*`, `services/s12-target`, 해당 테스트·결과 문서입니다. 팀 S12 규칙·워크플로 원본과 기존 S1/S4 실행 파일은 보존합니다. 팀 김대훈의 S12 요청 집계/health 기준선 계산, 개인 S1의 티켓·IP 소유권 확인/원복 구조를 재사용합니다.

## 인수 조건

1. 새 프로젝트와 빈 볼륨에서 전용 공격/정상 클라이언트의 실제 출발지를 확인합니다. 주소·포트·경로·실행 한도는 설정에서 읽고 비밀값은 Git 밖에 둡니다.
2. 정상 클라이언트 및 실제 n8n→포털 경로의 기준선을 별도로 측정합니다. 요청 기준은 정상 60초 최대 건수×3, 지연 기준은 max(p95×3, p95+300ms)입니다. 측정하지 않은 배포는 차단을 활성화하지 않습니다.
3. 기준 이하 요청은 무탐지, 기준 초과지만 health 정상이면 무차단·무티켓입니다. 정확한 N/N+1과 창 경계는 오프라인 규칙 검사로 별도 구분합니다.
4. 격리 대상의 제한된 자원 경합 조건에서 요청 수 초과와 실제 health 3회 연속 저하가 함께 성립할 때만 티켓·IP 차단을 확인합니다. 가짜 health 응답을 만들지 않습니다. 이는 **통제된 자원 경합 시험**이며 일반 서비스나 운영 환경 DDoS 방어 성능으로 주장하지 않습니다.
5. 공격 403, 별도 정상 출발지 200과 본문, 차단 후 지연 회복을 확인합니다. 정확한 티켓으로 원복 후 양쪽 200, 활성 조치·차단 0, 같은 티켓 restored를 대조합니다.
6. 승인받아 중지한 기존 Graylog·Wazuh 6개를 원래 ID로 재개합니다. 기존 MySQL ID/시작 시각과 VM 상태는 유지합니다.

## 실행 경계

- 최대 5 req/s, 동시 요청 2개, 90초, 기본 최대 240건입니다. 정상 대조 실패·STOP 파일·공격 IP 차단 관측 시 입력을 멈춥니다.
- 자원 경합은 전용 랩의 로컬 제어 파일로만 켜며 최대 150초 후 만료합니다. API 응답 차단 가드가 경합 처리보다 먼저 실행되고 대응 API는 경합에서 제외합니다. 운영 포털 코드에는 이 시험 경로를 추가하지 않습니다.
- 운영자 원복 키와 탐지 키는 분리합니다. 원문 n8n 실행 payload는 저장하지 않습니다. 티켓의 조치 성공과 외부 효과 관측은 서로 다른 증거입니다.
- 전체 완료 여부와 수치는 결과 문서/증적 생성 후 기록합니다. 이 문서는 작업 범위이며 실측 완료 증명이 아닙니다.
