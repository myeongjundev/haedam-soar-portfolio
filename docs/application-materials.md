# 김명준 이력서와 자기소개서 프로젝트 문안

2026-11-10 기준. 보안 관제·보안 엔지니어 지원서에 넣을 프로젝트 항목입니다. 지원 회사와 직무에 맞춘 동기, 개인 경력·학력·연락처는 별도로 작성합니다. 자기소개서의 회고 표현은 최종 제출 전에 본인의 경험과 말투에 맞게 확인합니다.

## 이력서 프로젝트 항목

**해담시청 민원포털 보안 관제와 자동 대응**

NoBugs 4인 팀 조장 · React/Flask 포털 구현 · S8/S10 시험 입력과 효과 검증 · 개인 재현 환경 구성

React·Flask 민원포털에서 발생한 공격 신호를 Graylog·Wazuh로 수집하고 n8n 대응과 티켓으로 연결하는 교육용 프로젝트입니다. 팀에서는 포털과 S8/S10 검증을 담당했고, 개인 전환에서는 한 PC의 Docker 환경에서 설치·탐지·대응·원복을 재현했습니다.

- React·Flask 기반 시민·담당자·관리자 화면과 API, 서버 세션·권한 제어, 감사 이벤트 및 IP 차단 경로를 구현했습니다.
- 팀 코드를 출처와 함께 선별해 포털·MySQL 및 관제 도구를 Docker Compose로 구성했습니다. 포털·DB는 새 클론과 빈 볼륨에서 마이그레이션, 가입·로그인, 재시작 후 세션 유지와 화면 수정·재빌드·원복을 확인했습니다.
- 개인 S8에서 실제 웹 탐색·로그인 실패를 Graylog와 n8n으로 연결해 IP 차단·티켓·원복을 검증했습니다. 공격 출발지 403, 정상 출발지 200, 해제 후 정상 응답을 대조했습니다.
- 개인 S7에서 Wazuh 파일 무결성 경보를 Graylog·n8n에 연결해 웹 파일 자동 복구와 시험 파일 격리를 구현·검증했습니다. 제어판의 입력·관찰·원복 흐름을 만들고 원천 경보, 파일 해시, HTTP 응답과 티켓 상태를 교차 확인했습니다.
- 민원 도배 시 계정의 작성 기능만 제한하는 H1을 추가했습니다. 제한된 계정의 조회와 다른 계정의 작성이 유지되는지, 운영자 해제 후 작성이 정상 복구되는지 확인했습니다.

**사용 기술:** React, Flask, MySQL, Docker Compose, Graylog, Wazuh, n8n, Python, GitHub PR. pfSense는 팀 환경에서 차단·원복을 검증했으며 개인 환경의 S10 전체 연결은 진행 중입니다.

**협업과 출처:** Wazuh 복구 도구와 티켓 저장소는 김상혁, Graylog·n8n 팀 설정은 김대훈의 구현을 활용했습니다. H1 아이디어와 제어판 흐름 참고는 반소람의 공유 자료에서 채택했습니다. Codex·Claude를 구현 보조와 PR 교차 검토에 사용했으며 개인 검증 기록을 별도로 남겼습니다.

## 수치를 넣을 때 사용할 문장

- 개인 S8 단일 회차에서 탐지 조건 충족부터 차단 API 응답까지 4.521초를 기록했으며, 별도 클라이언트로 차단 403·정상 200·해제 후 200을 확인했습니다.
- 개인 S7 제어판 실측에서 입력 직전 기록부터 자동 대응 효과 확인까지 파일 복구 8.211초, 추가 파일 격리 6.699초를 기록했습니다. 두 티켓 모두 원복 완료 상태를 확인했습니다.
- 개인 H1 단일 회차에서 탐지 조건 충족부터 작성 제한 API 응답까지 14.532초를 기록했습니다. 제한 계정의 작성 429·조회 200, 다른 계정의 작성 201, 해제 후 작성 201을 확인했습니다.

세 수치는 측정 시작·종료 기준이 다릅니다. 평균 처리 속도, 최초 공격부터 차단까지의 시간, 성능 개선율 또는 운영 환경 SLA로 바꾸어 쓰지 않습니다. H1의 429 관측 시각과 제한 API 응답 시각도 구분합니다.

## 자기소개서 문안 하나 문제 해결과 검증

해담시청을 가정한 4인 보안 관제 프로젝트에서 조장을 맡아 React·Flask 포털과 S8/S10 시험 입력 및 효과 검증을 담당했습니다. 프로젝트를 개인 환경으로 옮기면서 중점을 둔 것은 설치 명령이 끝나는 것과 실제 대응이 작동하는 것을 구분하는 일이었습니다.

S7에서는 이미지를 다시 빌드해도 기존 Docker 볼륨의 코드가 남아 실행 파일과 소스가 달라질 수 있었습니다. 팀원과 AI 도구의 검토 결과를 반영해 실제 볼륨과 빌드 이미지를 비교하고, 불일치가 있으면 새 시험 입력과 환경 재설정을 거부하도록 연결했습니다. 다만 진행 중인 사건의 파일 변조가 정상적인 원복을 막아서는 안 되므로 관찰·원복 경로에는 새 입력용 검사를 적용하지 않았습니다. 이후 진행 중 티켓과 변경된 대상의 거부 사유를 먼저 보여 주도록 검사 순서를 조정하고 회귀 테스트로 확인했습니다.

실측에서는 제어판의 성공 표시뿐 아니라 Wazuh 원천 경보, Graylog 이벤트, n8n 실행, 파일 해시와 티켓 상태를 대조했습니다. 기존 통합 버전에서 파일 복구와 격리를 각각 실행하고 두 티켓의 원복까지 확인했습니다. 최신 검사 순서 수정은 오프라인 테스트로 확인했으며 Docker 재실측과 구분해 기록했습니다. 이 경험을 바탕으로 변경한 코드와 실행 중인 상태가 일치하는지, 문제가 생겼을 때 복구 경로가 남아 있는지를 함께 확인하는 엔지니어가 되고자 합니다.

## 자기소개서 문안 둘 서비스 영향을 고려한 보안

보안 대응의 효과를 확인할 때 공격 요청이 막혔는지와 정상 사용자가 계속 서비스를 이용할 수 있는지를 함께 살폈습니다. 개인 S8에서는 공격 출발지의 요청이 403으로 차단되는 동안 정상 출발지는 200을 유지하는지 확인하고, 운영자 해제 후 두 출발지가 다시 정상 접근하는지 검증했습니다.

시청 민원 업무를 반영한 H1에서는 민원을 반복 등록하는 계정의 작성 기능만 제한했습니다. 팀원이 제안한 아이디어를 개인 환경에 구현하면서 로그인과 조회, 다른 시민의 작성까지 함께 막지 않도록 대응 범위를 나눴습니다. 실제 시험에서 제한 계정의 작성은 429, 조회는 200, 다른 계정의 작성은 201을 확인했고 해제 후에는 해당 계정도 다시 작성할 수 있었습니다.

이 과정에서 대응 API의 성공만으로 서비스 정상화를 판단하지 않고, 사용자별 실제 응답과 티켓의 종료 상태까지 확인하는 절차를 정리했습니다. 앞으로는 부분 실패와 재시도 상황에서도 같은 기준으로 대응 효과와 원복 여부를 확인할 수 있도록 검증 범위를 넓히고자 합니다.

## 개선점과 회고 문장 후보

**설치 재현성:** 팀 PC에 이미 존재하는 볼륨과 설정을 설치 완료의 전제로 삼지 않아야 한다는 점을 배웠습니다. 개인 환경에서는 초기화·설정 반입·현재 실행 파일 검사를 분리했고, 남은 전체 스택 새 설치 검증에서도 이 기준을 유지하려고 합니다.

**실패 진단:** 요청을 안전하게 거부하더라도 이유를 잘못 표시하면 운영자가 다른 문제를 고치게 됩니다. 진행 중 사건, 변경된 대상, 오래된 실행 파일을 구분해 보여 주는 것이 유지보수에 중요하다고 느꼈습니다.

**복구 판단:** 과거 성공 기록과 지금의 정상 상태는 다를 수 있습니다. 같은 사건의 파일 해시·HTTP 응답·티켓을 다시 확인하고 완료 처리하는 습관을 이어가고 싶습니다.

**다음 개선:** 개인 pfSense/S10 실측, 최신 제어판 수정 후 Docker 재검증, 중단·부분 실패 시험, 전체 README 새 환경 설치를 마친 뒤 결과를 갱신할 계획입니다.
