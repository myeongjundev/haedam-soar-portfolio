## 3. 연결 방식

[구성도](s10-lab.md#구성)를 참고하세요.

- 포털 GELF는 default 망으로, pfSense syslog UDP는 `pf-lan`으로 Graylog에 들어갑니다.
- Graylog는 `pfsense` 스트림(MATCH_INPUT)에 `pfsense-parse` 파이프라인을 붙입니다.
- S10 정의(같은 `src_ip`, 15분, `card(rule)>2`)가 발동하면 n8n `haedam-s8-s10` 웹훅(`X-S10-Detection-Key`)을 부릅니다.
- n8n은 다음 순서로 처리합니다.
  1. `haedam-32`: 중복 확인 → 티켓 detected 선기록
  2. `haedam-12`: 포털 IP 차단(`portal-response`, 응답망 CIDR+키)
  3. `haedam-14`: relay → SSH(고정 호스트 키, forced command) → 팀 도구 `block`
  4. 각 결과를 `haedam-10`으로 티켓에 기록
- 원복은 `haedam-50`(`X-S10-Operator-Key`)이 정확한 `ticket_id`의 pfSense `unblock`과 포털 `unblock`을 실행하고 기록합니다.

## 6. 실패한 시도와 해결

다음 결함은 모두 실제로 재현한 뒤 고쳤고, 고친 다음 다시 실측했습니다.

1. **Docker `internal` 망:** `DOCKER-INTERNAL` 규칙이 다른 대역을 목적지로 하는 bridge 프레임을 버려 라우팅 트래픽이 사라졌습니다. ARP만 통과했습니다. → `internal`을 끄고 masquerade도 끔(`7d39d2a`).
2. **Docker bridge 반사:** Docker bridge가 프레임을 되돌려 보내 게스트 MAC이 Docker 쪽 포트로 학습됐습니다. 그 결과 게스트로 가는 유니캐스트가 사라졌습니다. → 그 포트의 MAC 학습을 끔(`7d39d2a`).
3. **시리얼 셸:** pfSense 셸(tcsh)의 `resizewin`이 입력을 삼키고, 콘솔 줄 길이 제한도 있었습니다. → 명령을 base64로 나눠 보내 `/bin/sh`로 실행하고, 표지는 출력 줄에서만 읽음(`7d39d2a`, `5faa543`).
4. **Graylog 주소 풀:** 다른 프로젝트의 정지된 망이 기본 주소 풀을 모두 차지했습니다. → `graylog-backend` 서브넷을 설정값으로 고정.
5. **Graylog 6.1 규칙 번호:** MATCH_INPUT이 8번입니다. 9번으로 만든 잘못된 스트림은 삭제하고 다시 만들었습니다.
6. **팀 파이프라인 텍스트:** stage 줄이 쉼표 요약 형식이라 그대로는 문법 오류입니다. → `rule "x";` 줄로 펼쳐서 반입.
7. **Graylog 처리 순서:** Pipeline Processor가 스트림 라우팅보다 앞에 있어 스트림 연결 파이프라인이 실행되지 않았습니다. → 이 랩 Graylog에서만 순서 변경.
8. **pfSense 원복 판정:** 원복 흐름이 pfSense 해제 성공을 실패로 보고 기록 전에 중단했습니다. 그래서 티켓은 `responding`인데 pfSense는 해제됐고 포털 차단은 남은 상태가 됐습니다. → unblock은 재조회(config·table·rule 없음)로 판정(`d37287c`). 같은 티켓으로 원복을 재시도해 실제 상태와 티켓을 맞췄습니다(`S10REL-…`).

## 7. 미검증·남은 위험

- **하지 않은 실측:** 실제 Graylog 알림 재시도, n8n 실행 중 강제 종료, pfSense 차단 직후 도구 응답 유실(`changed:null`) 실측, 장시간·반복 성능, 다른 설정 값의 Docker 실측(오프라인 시험만).
- **grace 시간:** 같은 출발지에는 15분 grace 동안 알림이 다시 가지 않습니다. 같은 대상은 15분 간격으로 시험해야 합니다.
- **ISO 체크섬:** ISO SHA-256 `441005f7…5d51`은 팀 사본과만 같다고 확인했고, Netgate 공식 체크섬과는 대조하지 않았습니다.
- **두 대응의 관계:** 차단 중 공격자 요청은 pfSense에서 먼저 끊깁니다. 그래서 포털 차단의 효과는 차단 목록 조회로 확인했고, pfSense만 해제된 장애 상태에서는 HTTP 403으로 따로 확인했습니다.
