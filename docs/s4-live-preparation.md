# S4 개인 입력 도구와 실측 준비

2026-11-10 김명준·Codex. **오프라인 준비 완료, 개인 S4 실제 탐지·잠금·티켓·원복은 미실행**입니다. [S4 워크플로](s4-auto-workflows.md), [계약](s4-contract.md), [팀 출처](sources.md)를 함께 봅니다. S1 실측 PR #25의 검증 커밋 `6bc8ee1`에서 분리한 `codex/s4-live-input` 작업이며 S1 코드·검토 브랜치는 변경하지 않습니다.

후속 [세션 준비·증적 수집 도구](s4-session-evidence.md)에서 아래 단계 당시 미구현이던 계정/세션 준비와 잠금·티켓·원복 수집을 구현·오프라인 검증했습니다. 새 설정·private 보관·선택형 observer가 필요하므로 최신 설치는 후속 문서를 따릅니다. 아래 141/25 검사 결과와 미구현 설명은 PR #26 당시 기록입니다.

## 범위와 설정

작업 ID는 개인 `S4-INPUT-PREP`입니다. 과거 팀 작업표의 P01/B01/D01 완료 여부를 대신 갱신하지 않습니다. 수정 대상은 S4 설정·번들·새 입력 도구·검증·절차입니다. 포털 API, 탐지 정책, n8n 계약은 변경하지 않습니다.

- `infra/s4-settings.json`이 프로젝트·망·출발지·호스트 포트·계정·경로·간격의 원본입니다. 입력기는 별도 주소나 임의 계정을 CLI로 받지 않습니다.
- S1에서 확인한 관리 포트 문제를 S4에도 수정했습니다. `network_internal`은 default=false, clients/response/graylog_backend=true입니다. 공격/정상 클라이언트는 clients 망에만 연결합니다. 관리 포트는 기존 Compose의 127.0.0.1 바인딩을 유지합니다.
- `tools/s4_client.py`는 S1의 검증된 소켓 전송·중지·저장 함수를 재사용합니다. S1 파일을 수정하지 않습니다. 실제 실행은 Linux 개인 컨테이너, `HAEDAM_S4_PROJECT` 일치, `execution_enabled=true`가 모두 필요합니다.
- 성공 입력에 필요한 비밀번호는 stdin 한 줄로만 받고 메모리에서 사용합니다. 로그인마다 새 세션/CSRF를 얻고 성공 뒤 `/auth/me`에서 지정한 잠기지 않은 시민 계정인지 확인합니다. 비밀번호·쿠키·CSRF·원문 응답·예외 메시지는 증적에 기록하지 않습니다.
- HTTP 요청 상한, 실제 소켓 출발지, 무재시도, STOP 파일, 디렉터리 단위 `input.lock`, 증적 덮어쓰기 거부를 적용합니다. 403/429/리다이렉트·잘못된 응답이면 즉시 실패로 기록합니다. 입력 완료는 `end_to_end_status=not_run`입니다.

## 입력 유형

탐지는 **600초 안에 같은 username+src_ip에서 401과 200이 모두 있고 합계 6건 이상**입니다. 성공/실패 순서와 실패 5건 이상을 보장하지 않습니다. 아래는 다른 로그가 없는 동일 키 검색창을 전제로 한 기대값이며 실제 탐지 결과가 아닙니다.

| profile | 로그인 순서 | 기대 탐지 | HTTP 최대 요청 |
| --- | --- | --- | --- |
| boundary5 | 실패 4 → 성공 1 | 없음 | 12 |
| trigger6 | 실패 5 → 성공 1 | 있음 | 14 |
| success_first6 | 성공 1 → 실패 5 | 있음, 순서 미보장 확인 | 14 |
| failures6 | 실패 6 | 없음 | 13 |
| successes6 | 성공 6 | 없음 | 19 |
| failure1_success5 | 실패 1 → 성공 5 | 있음, 알려진 오탐 조건 | 18 |

간격은 중앙 설정의 10초입니다. health 1회, 매 로그인 전 세션 1회, 로그인 1회, 성공 후 세션 확인 1회를 요청 상한에 포함합니다. 같은 고정 대상 계정을 쓰므로 **run ID만 바꿔도 Graylog 검색 키가 달라지지 않습니다.** 유형을 연속 실행하면 경계값 결과가 오염됩니다. 도구의 lock은 동시 실행만 막고 검색창 만료나 Graylog 상태를 검사하지 않습니다.

## 지금 실행 가능한 오프라인 명령

루트에서 Python과 테스트 의존성이 있는 인터프리터를 사용합니다. 아래 명령은 컨테이너를 시작하거나 HTTP 요청을 보내지 않습니다.

```powershell
python tools/s4_lab.py check
python tools/s4_client.py --settings infra/s4-settings.json --run-id s4prep20261110 --profile boundary5
python tools/s4_client.py --settings infra/s4-settings.json --run-id s4prep20261110 --profile trigger6
python tools/s4_lab.py init --run-id s4prep20261110 --output .local/s4-prep-20261110
python tools/build_s4_workflows.py --check
python -m pytest tests -q
```

출력 폴더는 신규 `.local` 하위 경로여야 합니다. 기본값은 입력 실행 비활성입니다. 새 번들에는 별도 키의 `lab.env`, 설정, Compose overlay, Graylog/n8n 템플릿과 `input-packet.json`이 들어갑니다. 패킷의 `plan_argv`와 `input_argv`는 배열이며 생성 자체로 실행되지 않습니다. 이 번들은 계정 생성·실제 리소스 ID 연결·배포까지 마친 환경이 아닙니다. `.local`은 커밋하지 않습니다.

## 실제 배포 전부터 원복까지

1. PR #25/S4 변경의 독립 검토와 현재 실행 순서를 확인합니다. 15:53 KST 읽기 전용 조회에서 기존 Graylog/Wazuh/MySQL 7개가 실행 중이고 VM 프로세스도 유지됐습니다. 후보 TCP 포트 15070/19170/15770/22370/18170 리스너와 Docker 망 4개 겹침은 없었습니다. Windows 가용 메모리는 약 1.99GiB로, 동시 설치가 준비됐다는 뜻이 아닙니다. **기동 직전 RAM·포트·Docker/VM 라우팅을 다시 확인**하고 기존 서비스 중지 범위는 별도 실행 순서에 맞춥니다.
2. 대상 주소·망·계정·포트를 검토한 로컬 설정에서 입력을 명시적으로 활성화하고 **새 번들**을 생성합니다. 생성 후 설정이나 키를 부분 수정해 해시·import 파일을 섞지 않습니다. `bundle.json`의 환경변수 제거 목록을 현재 명령 프로세스에 적용하고 `compose_argv`로 설정을 먼저 검증합니다. 새 프로젝트/소유 볼륨만 사용합니다.
3. 새 포털 DB를 마이그레이션하고 대상/정상 시민 계정을 준비합니다. 정상 클라이언트에서 비밀번호 소유권을 확인하고 대상 세션 두 개 및 정상 세션을 별도로 유지합니다. 공격 출발지에서 미리 성공 로그인하면 탐지 키에 200이 추가됩니다. 세션 원문을 Git·증적 JSON에 저장하지 않습니다. 이 계정 준비/세션 유지 CLI는 아직 없습니다.
4. `tools/build_s4_workflows.py`의 `materialize`에 실제 Graylog 리소스 ID와 로컬의 별도 5개 키를 연결하여 개인 import를 만듭니다. 템플릿을 그대로 운영하지 않습니다. n8n 4개 흐름·자격증명을 연결하고 저장 설정 none·동시 실행 1을 확인합니다. 준비 중 탐지 스케줄은 비활성입니다.
5. 탐지를 활성화하기 전 같은 username+src_ip의 이전 로그가 600초 검색창에서 빠졌는지 확인합니다. **한 번에 한 profile만** 패킷 명령 배열로 실행합니다. 성공 입력의 비밀번호를 stdin으로 전달하고 명령행·출력에 넣지 않습니다. `--execute` 없는 명령은 계획만 출력합니다. STOP 파일은 번들의 runs 폴더에 만듭니다.
6. Graylog 원천 로그의 계정·출발지·401/200 건수와 입력 증적을 대조합니다. 마지막 필수 로그가 Graylog에 도착한 뒤 660초 이상 관찰하고 이벤트/티켓 0건 또는 실제 이벤트 ID를 기록합니다. 입력기가 끝났다는 이유만으로 탐지를 통과시키지 않습니다. 자동 잠금이 마지막 로그인 후 세션 조회보다 먼저 실행되면 입력 증적이 실패로 남을 수 있습니다. 이 경우 재시도로 로그를 늘리지 말고 로그인 기록과 잠금 시각을 별도로 대조합니다.
7. 탐지 후 대상 신규 로그인 거부·기존 두 세션 무효, 정상 계정 새 로그인/기존 세션 유지, 티켓·계정 ID·소유 조치를 같은 회차로 확인합니다. S4 잠금은 IP가 아니라 계정 전체에 적용됩니다. 현재 포털은 잠긴 계정 로그인도 401 `INVALID_CREDENTIALS`로 반환하므로 상태/소유권도 함께 확인합니다.
8. 원복 전 스케줄/알림과 대기 실행을 확인해 추가 대응을 멈춥니다. 현재 티켓으로 별도 원복 키를 사용해 승인 해제합니다. 새 로그인 성공, 옛 세션은 계속 무효, 비밀번호 유지, 정상 사용자 영향 없음, 티켓 restored·활성 조치 0을 대조합니다. 기존 입력이 검색창에서 만료되기 전 재활성화하지 않습니다.
9. 실측 시간·건수와 가린 화면을 저장하고 필요한 환경을 재개합니다. 이 단계의 수집기와 실제 실행은 후속입니다. 성공/실패 단일 유형, 계정/IP 혼합, 429 제외, 알려진 오탐 조건은 별도 깨끗한 검색창에서 확인합니다.
