# H1 개인 실측 · 2026-11-09

최종 판정: **실제 HTTP→Graylog→n8n→작성 제한·티켓→해제 통과**. 실제 개인정보 없이 격리 랩의 합성 시민으로 시험했습니다.

- 최종 실행: `H1-20261109T021122Z`, KST 11:11:22~11:12:43.
- Graylog 이벤트: `01M6Z1899TSW9JNVWP5Y5TAZAT`.
- 티켓: `T-20261109-0001`, data_origin `live`, n8n 제한 실행 `3`·해제 실행 `7`.
- 증거: [검증 JSON](evidence/h1-live-20261109.json), [원복 화면](evidence/h1-ticket-restored.png).
- 최종 실행 JSON의 source_sha256 항목은 해당 실행에 사용한 로컬 코드와 모두 일치합니다. 화면 캡처는 같은 티켓을 대상으로, 팀의 D PC 전용 안내 문구만 개인 랩 안내로 고친 뒤 촬영했습니다.
- 환경: Windows Docker Desktop, WSL 6GB, 개인 `haedam-h1-live`만 실행. MySQL 8.4, Graylog 6.1.16, OpenSearch 2.5.0, MongoDB 6.0.28, n8n 2.39.5.

각 회차는 개인 H1 볼륨을 새로 구성했습니다. 중간 코드·검증기 보완이 있으므로 동일 버전의 성능 표본 세 개로 평균을 내지 않습니다. 최종 실행만 공개 증적으로 선별했고 중간 JSON은 `.local/h1/`에 보존했습니다. 탐지는 15초 주기이며 이 세 관측값은 운영 성능 보장이 아닙니다.

조건 충족 시각은 실제 성공 이벤트 다섯 개 중 마지막 시각입니다. 판정은 Graylog 처리 시각, 제한 응답은 n8n이 포털 응답을 확인한 시각입니다. 별도 후속 HTTP에서 429와 정상 사용자 201을 확인했습니다. 시간 차 자체가 최초 429를 관찰한 시각을 뜻하지는 않습니다.

현재 티켓의 condition_met_at과 verified_at은 null입니다. 화면의 MTTD·MTTR 미측정은 그대로 유지하며, 위 수치는 원천 이벤트를 사용한 검증기의 별도 계산입니다. 직접 HTTP 효과 증거를 티켓의 effect 레코드로 연결하는 작업은 후속 개선입니다.

## 개발 검증과 한계

- SQLite 백엔드 65 passed / 4 skipped(동시성 검사 추가 전), 최종 일회용 MySQL 백엔드 **71 passed**. 사용자 행 잠금·다른 소유자 경쟁·이미 열린 세션의 오래된 snapshot 회귀 검사를 포함합니다.
- 일회용 MySQL에서 새 설치, `db check`, downgrade base → upgrade 통과. 기존 DB 데이터로 downgrade하지 않았습니다.
- 개인 계약·워크플로 테스트 **10 passed**. 기존 S8 생성물 7개와 H1 생성물 2개 일치 검사 통과. 기존 S8 전체 라이브 시나리오는 이번에 재실행하지 않았습니다.
- 임계값 5건/10분은 합성 랩 기준입니다. 실제 시민 정상 사용량·오탐률·운영 임계값 검증은 아닙니다. 비동기 탐지의 지연 동안 추가 등록이 가능하며 동기식 속도 제한은 별도 과제입니다.
- 자동 시험의 장애 범위는 조치 전 티켓 저장소 장애입니다. 조치/해제 성공 직후 기록 실패의 복구, 다중 n8n 인스턴스 경쟁은 독립 검토 대상으로 남겼습니다.
- 외부 Discord 알림, 개인 Wazuh/S7, 개인 pfSense/S10, H2~H4는 이번 통과 범위에 없습니다. pfSense는 이 PC Docker/WSL의 KVM 부재를 확인했으며 기존 VMware VM은 변경하지 않았습니다.
- payload 행 0은 조회한 실행 테이블의 결과입니다. SQLite의 삭제된 디스크 영역까지 보안 삭제했다고 주장하지 않습니다.
- 작업 종료 후 개인 H1 컨테이너를 정지하고 볼륨을 보존했습니다. 기존 학원 컨테이너 8개를 복구하고 Graylog·n8n·Wazuh 대시보드 HTTP 200, MySQL TCP 연결을 확인했습니다. 기존 환경 전체 시나리오를 다시 시험한 것은 아닙니다.
