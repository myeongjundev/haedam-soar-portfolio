## 코드에서 확인한 설정 차이

1. **탐지 연결:** S1/S4 정의는 `REPLACE_haedam-portal_stream_id`, S12는 팀 스트림 ID가 들어 있으며 셋 모두 `notifications: []`입니다. 개인 `configure`가 실제 스트림·알림 ID를 생성해 연결하고 시험 전까지 예약을 정지해야 합니다.
2. **수신 인증:** S1/S4/S12 Webhook은 현재 `headerAuth`를 선언하지만 credential은 `BIND_LAB_WEBHOOK_AUTH`입니다. S1/S12 알림 파일은 host.docker.internal 주소와 비어 있는 인증 설정을 사용합니다. 개인 내부 DNS·전용 키·URL allowlist를 맞춰야 합니다. S4 개인 알림 템플릿도 준비해야 합니다. 팀 README의 과거 무인증 검사 문구와 현재 JSON 선언은 구분합니다.
3. **실제 동작 모드:** 주 워크플로는 `dry_run: true`, `store_real: false`에서 시작합니다. 단순 import로 실제 차단·티켓이 만들어지지 않습니다. 개인 배포 시 고정한 모드와 대상 허용 목록을 사용하고 요청 본문만으로 임의 대상·실행 모드를 바꾸지 못하게 해야 합니다.
4. **공통 의존성:** S1은 30→10/12/11, S4는 31→10/13/11, S12는 20→10/12/11입니다. ID 중복과 하위 호출 게시 상태를 확인합니다. 티켓(10), 효과 보고(40), IP 해제(50)는 S8에서 검증한 개인 인증·소유권·HTTP 실패 처리 구조를 참고하되 S8 전용 케이스 가드를 그대로 재사용하지 않습니다. Discord 발송은 개인 시험에서 비활성으로 둡니다.
5. **S4 해제:** 원본 50은 IP 차단 해제용이며 계정 잠금 해제가 아닙니다. 원본은 live release도 비활성이고 Webhook credential 연결도 없습니다. 포털의 관리자 unlock/reset 또는 사용자 ID 기반 response reset 경로와 별도 승인, 티켓 `lock` 조치 종료를 설계해야 합니다. API 경로는 `haedam-portal-backend/src/haedam_portal/integration/__init__.py`와 `admin/__init__.py`를 기준으로 합니다.
6. **대상·묶음:** S1 탐지는 username+src_ip, 주 워크플로 티켓 group_key는 username입니다. 다른 IP의 같은 계정이 섞일 때 티켓·조치 소유권이 맞는지 시험해야 합니다. S4는 계정 자원의 전역 잠금이므로 IP별 탐지 키와 계정별 조치 소유권을 구분합니다. 팀 보호 주소 목록만으로 개인 대상 제한을 대신하지 않습니다.
7. **측정 시각:** 알림의 `${event.timestamp}`를 임계 충족 시각으로 자동 인정하지 않습니다. 마지막 필수 입력의 도착·집계 충족 시각과 탐지 시각을 증적으로 대조하고, 없으면 시간을 미측정으로 남깁니다.

## 개인 랩 공통 설정과 인수 조건

- 새 프로젝트·볼륨·합성 계정·공격/정상 클라이언트를 사용합니다. IP·서브넷·포트·계정·URL·경로는 공통 설정에서 읽고 코드에 새 배포 상수를 넣지 않습니다. 현재 사용 중인 S10·S7·S8·H1 망과 겹치지 않는 값은 배포 직전 확인해 선택합니다.
- 클라이언트 실제 소켓 출발지와 포털/Graylog의 src_ip가 일치해야 합니다. 신뢰하지 않는 X-Forwarded-For 헤더로 출발지를 흉내 내지 않습니다.
- 포털 RESPONSE_ALLOWED_CIDRS는 개인 n8n 대응 주소로 제한하고 포털·티켓·탐지·운영자 키는 분리합니다. n8n 실행 payload 비저장과 컨테이너 내 임시 credential 삭제를 확인합니다.
- 케이스를 하나씩 활성화합니다. S1/S4/S8 로그인 입력은 서로 영향을 줄 수 있으므로 다른 탐지 정의를 확인 없이 함께 켜지 않습니다.
- 사전 원복 경로와 정상 대조를 준비합니다. 대응 API 200만으로 효과를 통과 처리하지 않습니다. 파일 존재·JSON 파싱·오프라인 판정을 실제 Graylog/n8n 실행으로 기록하지 않습니다.

## S1 시험 절차

**규칙:** 30분 내 같은 username+src_ip의 `login-bruteforce`, status 401 **9회 이상**. 실행 60초, 알림 유예 30분. 429는 제외합니다. 현재 구현의 대응은 계정 잠금이 아니라 **출발지 IP 차단**입니다.

1. 시험/정상 계정과 별도 출발지, 이전 30분 창의 해당 키 입력이 없는지 확인합니다. 정상 로그인·홈 200, 활성 조치 없음과 티켓 시작 상태를 기록합니다.
2. 독립 boundary 계정에서 401 8회를 기록합니다. 포털 발생과 Graylog 수신이 8건인지 대조하고 마지막 401 수신 후 1,860초 동안 무탐지·무차단을 관찰합니다. 빠진 이벤트를 같은 회차에 보충하지 않습니다.
3. 새 trigger 계정/회차에서 401 9회를 입력합니다. 기존 팀 도구의 100초 간격이면 첫 입력부터 9번째까지 최소 800초입니다. 시간 단축을 위해 임계값이나 창을 바꾸면 별도 정책 실측으로 표시합니다.
4. 같은 이벤트의 Graylog→n8n→티켓→IP 차단을 대조합니다. 공격 출발지 403, 별도 정상 출발지의 로그인·홈 200을 확인합니다.
5. 탐지 예약을 정지하고 동일 이벤트 재전송의 추가 조치 없음, 다른 티켓 해제 거부를 확인합니다. 소유 티켓의 운영자 해제 뒤 양쪽 200, 활성 차단/조치 0, 티켓 restored를 대조합니다.
6. 별도 시험으로 429 제외, 서로 다른 계정/출발지의 5+4회 분리, 창 밖 입력을 확인합니다. 로그 수신 누락·지연은 탐지 실패와 구분해 남깁니다.

기존 `tools/s1_input_probe.py`는 `/home/kali/.../b_scenario_probe.py`의 고정 SHA, Kali 환경, 팀 대상·출발지를 요구합니다. 개인 Docker 클라이언트용 입력기로 전환하기 전 `--execute`를 사용하지 않습니다.

## S4 시험 절차

**현재 규칙:** 10분 내 같은 username+src_ip에서 실패 401·성공 200 모두 존재, 합계 **6건 이상**. 실행 60초, 유예 10분. 이 집계는 **순서를 검사하지 않으며 성공→실패도 발동**합니다. 이번 준비에서는 기존 의미를 보존하고 ‘실패·성공 혼재’ 정책으로 시험합니다. 엄격한 실패→성공 정책으로 바꾸려면 별도 설계·규칙 검증이 필요합니다.

1. 전용 비관리자 `zz_` 계정과 정상 계정을 준비합니다. 팀 세션 도구는 staff 역할과 정상 계정을 전제로 하므로 개인 계정 준비와 설정 매개변수화가 선행됩니다.
2. 시험 전에 대상 계정의 기존 로그인 세션 A를 보유합니다. 그 로그인도 같은 탐지 키/창에 들어갈 수 있으므로 다른 출발지로 준비하거나 창을 분리하고 수신 이벤트 수를 대조합니다.
3. 독립 boundary 회차에서 실패 4+성공 1은 미탐지, trigger 회차에서 실패 5+성공 1은 탐지·티켓·잠금을 확인합니다. 팀 도구의 입력 간격은 60초입니다.
4. 잠금 후 기존 세션 A의 인증 해제, 올바른 비밀번호로도 신규 로그인 거부, 다른 정상 계정의 세션·로그인 유지와 잠금 API의 세션 회수 결과를 확인합니다. 응답은 단순 상태 코드뿐 아니라 실제 사용자 식별/인증 여부를 대조합니다.
5. 탐지를 정지하고 승인된 관리자 unlock(오탐 해제) 또는 reset(비밀번호 변경)을 선택합니다. 새 로그인 성공과 티켓 조치 종료를 확인합니다. **폐기된 옛 세션은 복구하지 않으며 계속 무효**여야 합니다.
6. 성공→실패 역순도 현재 규칙에서 탐지되는지 확인해 한계로 기록합니다. 실패만 6건, 다른 IP의 성공 혼합, 429 포함, 다른 계정 혼합은 별도 대조합니다.

`lab/s1s4/s4_session_round.py`에는 팀 HOST/PORT/NORMAL/정상 계정이 남아 있습니다. 개인 배포용으로 매개변수화하기 전에는 PLAN ONLY만 사용합니다. 도구의 `external_ticket_action_closure_verified:false`는 클라이언트 검사만으로 티켓 종료를 증명하지 못한다는 뜻입니다.

## S12 시험 절차

**현재 팀 값:** 요청 집계는 60초 창의 `web.request` **count > 93**, 실행 30초, 유예 60초입니다. n8n은 별도로 health K=3회, 2초 간격, timeout 5초, 팀 기준 2,000ms를 사용합니다. 요청 수 초과만으로 차단하지 않고 연속 health 저하를 요구합니다. 이 값들을 개인 환경의 실측 기준선으로 재사용하지 않습니다.

1. 포털 준비 후 정상 클라이언트→health와 n8n→health 경로를 각각 측정합니다. 같은 경로·주기·시간대의 median/p95/max, 상태·본문, 실제 수신 `web.request` 수를 저장합니다. 정상 구간에서 K회 연속 초과가 없는지도 확인합니다.
2. `s12_baseline_calc.py`로 CSV를 계산합니다. 요청 임계 후보는 60초 최대 요청 수의 3배 올림, 지연 후보는 max(p95×3, p95+300ms)입니다. 후보가 정상 변동을 오탐하는지 확인한 뒤 근거와 함께 확정합니다. n8n 경로 기준선은 클라이언트 경로 수치로 대신하지 않습니다.
3. 확정된 요청·지연 기준과 K·timeout을 개인 설정에 넣습니다. 초기 부하 계획은 1→2→5 req/s, 단계 30초, 총 90초, 동시성 2로 제한합니다. 이는 제안된 시작 한도이며 실행하거나 효과를 보장한 값이 아닙니다. 정상 대조 오류·메모리 부족·중지 파일·차단 관측 때 즉시 중지하도록 준비합니다.
4. count가 N 이하일 때 무탐지, N 초과지만 health 정상일 때 무차단을 확인합니다. 건강한 서버가 제한 부하에 영향을 받지 않으면 그것이 정상 결과이며 차단 성공으로 쓰지 않습니다.
5. 실제 차단 경로를 확인하려면 격리된 개인 대상에서만 재현 가능한 저하 조건을 별도 정합니다. 임계값을 임의로 낮추거나 가짜 health 응답을 실제 가용성 장애로 기록하지 않습니다. 합성 고장 주입은 별도 시험으로 구분합니다.
6. count>N과 K회 연속 저하가 함께 확인된 회차에서 티켓→공격 IP 403·정상 출발지 200/정상 본문을 확인합니다. 내부 n8n 경로 회복만으로 정상 사용자 효과를 완료 처리하지 않습니다.
7. 탐지를 정지하고 정확한 티켓의 IP 차단을 해제합니다. 공격·정상 양쪽 HTTP/지연 회복, 활성 조치 없음, restored를 확인합니다. 실제 저하·차단을 재현하지 못했으면 탐지/무차단 검증까지만 기록합니다.

`s12_probe.py`·`s12_flood.py`는 기본 팀 URL을 가지며 **기본 실행이 네트워크 요청**입니다. 개인 대상·실제 source·중지 한도를 지정하는 실행기를 준비하기 전 실행하지 않습니다. `--help`만 오프라인입니다. 부하 도구의 절대 상한 100 req/s는 개인 시험의 권장 부하가 아닙니다.

## 증적과 완료 판정

회차마다 코드·설정 해시, 프로젝트, 대상/정상 클라이언트, 입력 수·마지막 필수 입력 시각, 원천 이벤트 수·ID, Graylog 이벤트, n8n execution, ticket ID, 실제 효과, 정상 대조, 원복 결과를 연결합니다. 비밀번호·쿠키·CSRF·민원 원문은 저장하지 않습니다.

결과는 `not_run / blocked / failed / passed`로 구분합니다. 탐지 시간은 조건 충족→Graylog 생성, 대응 시간은 조건 충족→API 응답 또는 효과 관측 중 실제 측정한 종료점을 적습니다. 회복·티켓 종료를 확인하지 못하면 전체 passed로 표시하지 않습니다.
