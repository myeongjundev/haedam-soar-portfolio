## 실제 실패와 수정

1. **컨테이너 health는 정상인데 호스트 접속 불가:** 네 망 모두 internal인 최초 구성에서 localhost 포트가 게시되지 않았습니다. `network_internal` 중앙 설정으로 관리 bridge만 일반망으로 두고, 클라이언트·응답·Graylog 저장망은 internal로 유지했습니다. 실제 포트 바인딩과 HTTP 접속을 확인했습니다.
2. **로그 수집 보조 도구의 응답 해석 오류:** Graylog 검색에 `Accept: application/json`이 빠졌습니다. 8회 입력은 실제로 수집됐지만 보조 도구가 이를 읽지 못했습니다. 헤더를 추가하고 탐지 예약을 다시 켠 뒤 31분 관찰을 처음부터 수행했습니다.
3. **실제 n8n이 빈 HTTP 200을 반환:** 최초 9회에서 Graylog 이벤트·알림은 발생했지만 티켓은 0건이었습니다. 진단용 직접 전달도 동일했고, 임시 추적으로 포털 조회 하위 흐름의 마지막 IF false 출력이 부모의 출력 0으로 전달되지 않는 것을 확인했습니다. 개인 생성기에 반환 Code 노드를 추가했습니다. 오프라인 실행기도 연결 없는 두 번째 출력을 정상 반환으로 취급하지 않도록 바꿨습니다.
4. **확인 도구가 생성된 티켓을 놓침:** 목록 요약에 없는 `username`으로 필터링해 티켓 0건으로 잘못 보고했습니다. 상세 API를 읽도록 고쳤습니다. 실제 자동 차단은 실행 ID 15에서 15:28:42에 이미 완료됐습니다. 15:31:29 진단용 직접 재전달(실행 ID 25)은 `duplicate_no_action`이며 새로운 차단·티켓을 만들지 않았습니다. 이 진단은 최초 자동 차단의 근거로 사용하지 않습니다. 증적에는 잘못된 조회값을 신뢰할 수 없는 모니터 값으로 명시하고 원래 기록을 보존했습니다.

원래 팀 JSON은 수정하지 않았습니다. 임시 추적은 개인 n8n에서만 수행했고, 첫 진단 실행 10~13과 후속 진단·원복 실행 25~37의 payload를 제거한 뒤 저장 설정을 none으로 되돌렸습니다. 최초 자동 차단은 실제 Graylog 알림으로 발생했고, 이후 진단용 직접 재전달과 구분됩니다. UI의 효과 확인 값은 미측정이며 독립 HTTP probe 결과는 별도 JSON에 보관합니다.
