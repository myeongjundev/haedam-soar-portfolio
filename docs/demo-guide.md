시간 수치는 각 결과 문서의 **단일 회차·시작/종료 정의**를 사용합니다. S7의 효과 확인 시간과 다른 사례의 차단 API 응답 시간을 같은 성능 지표로 비교하지 않습니다.

## 실제 시연을 한다면

우선 **개인 S7 한 사례**를 선택합니다. 설치와 재개는 [제어판 설치 절차](panel-lab.md)와 [랩 선택 안내](installation-guide.md)를 따릅니다. 이번 문서 작성 중에는 Docker·VM을 조작하거나 새 실측을 하지 않았습니다.

1. 같은 worktree·프로젝트의 자동 S7이 준비되었는지 확인합니다. 프로젝트·포트·에이전트가 다르면 입력하지 않습니다. 기존 학원 환경을 임의로 중지하지 않습니다.
2. 제어판·포털·해담 티켓 화면을 엽니다. 로그인과 환경 설정 파일은 화면 공유에 노출하지 않습니다.
3. **환경 확인 → 시험 입력(파일 변조 하나)**을 누릅니다. 입력 직전 프로젝트와 대상 경로를 읽어 확인합니다.
4. **탐지·대응 확인**에서 같은 회차의 Wazuh 경보·Graylog 이벤트·티켓 연결과 파일 복구/HTTP 효과를 확인합니다. 기존 성공 회차를 새 실측처럼 설명하지 않습니다.
5. **원복 완료** 후 같은 티켓의 `restored`, 정상 파일·HTTP, 잔여 격리물 없음을 확인합니다. 증적 JSON을 내려받습니다. 컨테이너 정지는 원복을 대신하지 않습니다.

환경 확인이 실패하면 입력을 반복하지 말고 오류를 기록합니다. 관제 화면이 열리지 않으면 위 저장된 증적을 **이전 실측 기록**이라고 설명하며 보여줍니다. 새 시연 통과로 표시하지 않습니다.

두 번째로 S8을 선택할 때는 [전체 검증 절차](s8-lab.md)를 확인합니다. 마지막 공격 입력 후 15분 재시험 대기와 **개인 티켓 저장소를 잠시 중지하는 장애 시험**이 포함되므로 빠른 화면 시연 명령으로 무심코 실행하지 않습니다. S1의 긴 집계창, S4의 600초 검색창, S12의 새 기준선 측정도 즉석 5분 시연과 구분합니다.

## 예상 질문과 답변 근거

**왜 Graylog와 Wazuh를 함께 썼나요?**

Wazuh는 파일 무결성 경보와 agent Active Response를, Graylog는 앱 이벤트와 전달된 경보의 검색·탐지를 담당합니다. n8n은 티켓과 조치를 연결합니다. 개인 S7은 FIM 즉시 대응이며 팀의 HTTP 접근 상관 정책과는 다릅니다. [S7 구조](s7-auto-lab.md).

**왜 티켓을 먼저 만드나요?**

어떤 사건이 조치를 소유하는지 남기기 위해서입니다. 기록이 실패하면 조치를 보류하고, 원복에서도 해당 티켓과 현재 소유권을 대조합니다. [S8 계약](s8-contract.md), [S4 계약](s4-contract.md).

**계정 잠금과 IP 차단은 무엇이 다른가요?**

S1은 시험 출발지 IP의 접근을 제한하고 S4는 계정을 잠그며 기존 세션도 회수합니다. 원복으로 계정 잠금은 풀지만 이미 무효화된 옛 세션을 되살리지는 않습니다. [S4 결과](s4-results.md).

**차단 API가 200이면 성공 아닌가요?**

API 수락과 실제 효과는 다릅니다. 공격·정상 클라이언트의 응답, 파일 해시나 계정 세션, 티켓 상태를 따로 대조했습니다. 화면 MTTD/MTTR이 비어 있는 경우 외부 증적에서 계산한 시간을 사용했습니다.

**S12로 DDoS 방어 성능을 증명했나요?**

아닙니다. 합성 요청과 통제된 공유 자원 경합에서 탐지·대응·원복 흐름을 확인했습니다. 차단 후 입력도 멈췄으므로 지속 공격 상태의 처리량 보장으로 일반화하지 않습니다. [S12 한계](s12-results.md).

**pfSense도 일반 Docker 서비스인가요?**

Docker 컨테이너 안에서 QEMU VM으로 실행한 pfSense CE입니다. 순수 Linux 컨테이너의 pfSense 서비스라고 설명하지 않습니다. 실제 두 경로의 차단·해제 근거는 [P04/S10](s10-results-20261110.md)에 있습니다.

**전부 혼자 만든 건가요?**

팀 코드·탐지 정책·티켓 구현을 바탕으로 개인 환경과 검증 도구·보완을 만들었습니다. 팀원 담당, 제어판·시청 특화 아이디어 출처, Codex·Claude 도움을 [출처](sources.md)에 분리했습니다.

**지금 새 PC에서도 완전히 설치된다고 검증했나요?**

사례별 개인 랩 실측과 새 원격 클론의 의존성·마이그레이션·테스트·설정 해석까지 확인했습니다. 최종 main에서 모든 서비스를 새로 기동하는 통합 재현은 아직 남았습니다. [새 클론 검사 범위](installation-audit-20261111.md).
