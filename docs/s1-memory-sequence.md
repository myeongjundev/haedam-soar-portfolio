# S1 실측 전 메모리 확보와 실행 순서

**11/10 후속 실행 완료:** 사용자가 기존 Graylog·Wazuh만 일시 정지하도록 허용한 뒤 이 순서로 S1 실측과 기존 6개 컨테이너 재개를 수행했습니다. VM·기존 MySQL은 유지했습니다. [최종 결과](s1-results.md). 아래 미실행·읽기 전용 설명은 승인 전 사전 점검의 이력입니다.

2026-11-10 김명준·Codex. **이번 작업은 조회와 계획만 수행했으며 기존 Docker·VM은 중지·재시작·설정 변경하지 않았습니다.** 아래 중지/재개는 사용자가 대상과 시점을 지정한 뒤의 절차입니다. 현재 조건을 유지하려면 S1은 여유 있는 별도 호스트에서 실행합니다.

## 읽기 전용 재확인

| 범위 | 관측값 | 해석 |
| --- | --- | --- |
| Windows | 총 15.85GiB, 가용 2.40GiB | 이전 2.21GiB에서 변동. 고정 여유로 보지 않음 |
| Docker | 한도 약 5.79GiB, 기존 7개 사용량 합계 약 4.37GiB | 약 1.42GiB 차이는 실제 가용 메모리가 아님 |
| `9_graylog` | `gl-graylog`, `gl-mongo`, `gl-opensearch` 합계 약 2.57GiB | S1의 새 Graylog와 별도인 기존 스택 |
| `wazuh-lab` | `wazuh-dashboard`, `wazuh-manager`, `wazuh-indexer` 합계 약 1.74GiB | S1에는 필요하지 않지만 기존 실습에 사용 중일 수 있음 |
| `7_test_class` | `flask_mysql` 약 53MiB | 회수 효과가 작으며 학원 데이터/연결 유지 우선 |

Docker `ps`, `stats --no-stream`, `info`와 Windows OS 메모리만 조회했습니다. VM 내부 상태·예약 메모리·업무 진행 여부는 확인하지 않았습니다. 호스트 메모리와 컨테이너 메모리는 중복되므로 합산하지 않습니다. 기존 7개와 S1 9개 서비스의 동시 기동은 보류합니다. S1은 Java 힙만 합계 1GiB이며 native/DB/n8n/빌드 메모리가 추가됩니다. 실제 최대 사용량은 아직 측정하지 않아 최소 RAM이나 회수 후 성공을 단정하지 않습니다.

## 기존 환경 보존 조건을 유지하는 경로

1. 충분한 여유가 있는 별도 호스트가 있다면 검토된 개인 브랜치와 설정만 가져옵니다. 기존 키·DB·볼륨은 복사하지 않습니다. 새 번들/비밀값을 생성합니다.
2. 그 호스트에서 메모리, Docker 한도, 프로젝트 이름, 포트 5개와 망 4개 충돌을 다시 확인합니다. 현재 PC의 통과 결과를 다른 호스트에 적용하지 않습니다.
3. 아래 단계별 설치와 실측을 진행합니다. 별도 호스트가 없다면 오프라인 준비까지만 유지하고, 같은 PC 순차 실행에 필요한 중지 대상/시점을 정합니다.

## 같은 PC에서 순차 실행할 때의 후보 순서 — 아직 실행하지 않음

1. **진행 중 작업 확인:** 기존 실습/자동 대응/티켓 원복이 끝났는지 확인하고, 시작 전 실행 중인 컨테이너와 프로젝트·health를 기록합니다. 진행 중이면 기다립니다. 종료됐던 컨테이너를 나중에 임의로 시작하지 않습니다.
2. **호스트 앱 정리:** 사용자가 저장을 마친 불필요한 브라우저 탭·IDE 창 등부터 정리하고 RAM을 다시 확인합니다. 이 단계만으로 Docker 한도가 늘어나는 것은 아닙니다. 프로세스를 강제 종료하지 않습니다.
3. **기존 Graylog 후보:** 사용자가 허용한 경우에만 `9_graylog`의 소비자인 Graylog부터, 다음 OpenSearch/MongoDB를 정상 정지합니다. 현재 사용량 약 2.57GiB는 예상 회수 참고값이며 실제 회수량이 아닙니다. 데이터·볼륨·네트워크는 보존합니다.
4. **기존 Wazuh 후보:** 여전히 여유가 부족하고 사용자가 허용했다면 `wazuh-lab`의 dashboard → manager → indexer 순서로 정상 정지한 뒤 다시 측정합니다. 약 1.74GiB 사용량도 보장되는 회수량은 아닙니다.
5. **VM은 별도 판단:** S1 자체는 Compose 내부망을 쓰므로 pfSense VM을 요구하지 않습니다. VM을 중지해야 할 정도라면 다른 작업의 경로 의존성을 먼저 확인하고 사용자가 지정한 VM만 정상 종료합니다. 현재 VM을 식별 없이 중지하거나 WSL 전체를 종료하지 않습니다. `flask_mysql`는 기본 유지합니다.
6. **기동 전 판정:** 호스트 가용 RAM과 Docker 사용량·한도, 기존 서비스 정지 상태, 새 S1의 망/포트/이름을 다시 확인합니다. 여유가 불명확하면 추가 설치를 보류합니다. Docker 메모리 상향, swap 확대, `prune`, 볼륨 삭제를 해결책으로 자동 실행하지 않습니다.

위 후보는 명시된 기존 프로젝트의 정상 정지/재개만을 위한 순서입니다. 모든 컨테이너를 선택하는 일괄 명령이나 `down -v`는 사용하지 않습니다.

## 새 S1 설치·실측·정리

실행 명령과 변수는 [S1 실측 준비](s1-live-preparation.md)의 새 번들 `compose_argv`를 사용합니다. 서비스 이름은 해당 Compose 구성에서 확인합니다. 단계를 나누는 것은 시작 순간의 동시 부하를 줄이는 방법이며 최종 필요 메모리를 줄이지 않습니다.

| 단계 | 동작 | 다음 단계로 가기 전 확인 |
| --- | --- | --- |
| 1 | 검토된 커밋 고정 → 새 번들 → Compose config 확인 → 필요한 이미지 준비/빌드 | 빌드 실패/OOM 없음, 기존 프로젝트에 영향 없음 |
| 2 | `db`, `graylog-mongo`, `graylog-search`부터 기동 | 각 health·메모리 안정, 반복 재시작/OOM 없음 |
| 3 | `portal`, `ticket-store`, `graylog` 기동 | DB 마이그레이션·앱/관제 health, 메모리 재확인 |
| 4 | `n8n`, `attacker`, `normal` 기동 | 9개 모두 예상 상태, 정상 요청 가능, 사용량·호스트 여유 기록 |
| 5 | 키/자격증명·실제 ID 연결·게시/인가 확인 → baseline | 공격 입력 전 정상 사용자 로그인과 로그 전달 확인 |
| 6 | 경계 8회·관찰 → 9회 탐지 → 차단·티켓 → 정상 대조 → 탐지 예약 정지 → 소유 티켓 원복 | 입력/이벤트/티켓/HTTP 효과/정상 로그인 일치, 최소 56분+설치·원복 시간 확보 |
| 7 | 원복 증적·최종 상태 저장 → 이번 S1 프로젝트만 정상 정지 | 미원복 조치가 있으면 완료로 표시하지 않고 복구 절차부터 진행 |
| 8 | 앞서 정지한 기존 자원만 재개 | Graylog: Mongo/OpenSearch health → Graylog. Wazuh: indexer health → manager/dashboard. 실제 기존 설정의 의존성을 우선하며 기동 전 기록과 대조 |

각 단계에서 가용 RAM 급감·지속적인 paging·서비스 health 실패·OOMKilled·재시작 증가가 보이면 입력을 시작하지 않습니다. 이미 대응이 진행됐다면 먼저 해당 티켓의 원복 상태를 확인합니다. 오류 해결을 위해 기존 프로젝트를 임의로 재시작하지 않습니다. 메모리 실측은 기동 직후와 입력/탐지/원복 중 각각 남겨 다음 설치의 예산 근거로 사용합니다.
